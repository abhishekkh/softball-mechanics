### Pattern 2: Rate Limiting via Next.js Middleware

**What:** Stateless per-IP, per-window counter using Edge-compatible headers. Since Vercel serverless is stateless, in-memory counters reset per instance — acceptable for this app's scale. The decision says "do not build a custom solution" — use `NextResponse` primitives directly in `src/middleware.ts`.

**Pattern (add to existing middleware.ts):**
```typescript
// Simple sliding-window rate limiter for sensitive routes
// Uses an in-memory Map (resets on cold start — acceptable for v1)
const rateLimitMap = new Map<string, { count: number; resetAt: number }>()
const RATE_LIMIT_WINDOW_MS = 60_000  // 1 minute
const RATE_LIMITS: Record<string, number> = {
  '/api/upload/presign': 10,  // 10 uploads/minute/IP
  '/api/analysis': 5,         // 5 analysis submissions/minute/IP
  '/api/analysis/vlm-eval': 3, // 3 VLM calls/minute/IP (Gemini cost control)
}

function checkRateLimit(ip: string, path: string): boolean {
  const limit = RATE_LIMITS[path]
  if (!limit) return true  // No limit for this path

  const key = `${ip}:${path}`
  const now = Date.now()
  const entry = rateLimitMap.get(key)

  if (!entry || now > entry.resetAt) {
    rateLimitMap.set(key, { count: 1, resetAt: now + RATE_LIMIT_WINDOW_MS })
    return true
  }

  entry.count++
  if (entry.count > limit) return false
  return true
}
```

Note: `rateLimitMap` is module-level in the Edge middleware — it persists for the lifetime of the Edge worker instance. This is the simplest approach without Upstash. It does not protect against distributed attacks across multiple Vercel instances, but it does protect against single-user abuse (the primary threat for this app at v1 scale).

### Pattern 3: React Error Boundary

**What:** Wrap client components that can fail at runtime (ReviewPageClient, UploadPageClient) in an error boundary to prevent full-page crashes.

**Next.js App Router compatible pattern:**
```typescript
// src/components/ErrorBoundary.tsx — 'use client' class component
'use client'

import { Component, type ReactNode } from 'react'

interface Props { children: ReactNode; fallback?: ReactNode }
interface State { hasError: boolean; error: Error | null }

export class ErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false, error: null }

  static getDerivedStateFromError(error: Error): State {
    return { hasError: true, error }
  }

  componentDidCatch(error: Error, info: { componentStack: string }) {
    // Log without exposing to client — structured context
    console.error('[ErrorBoundary] Component error:', { message: error.message, stack: info.componentStack?.slice(0, 200) })
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? (
        <div className="p-6 text-center">
          <p className="text-sm text-red-600 font-medium">Something went wrong loading this page.</p>
          <button onClick={() => this.setState({ hasError: false, error: null })} className="mt-3 text-sm text-blue-600 hover:underline">
            Try again
          </button>
        </div>
      )
    }
    return this.props.children
  }
}
```

**Placement:**
- Wrap `ReviewPageClient` usage in `src/app/(app)/review/[videoId]/page.tsx`
- Wrap `UploadPageClient` usage in `src/app/(app)/upload/page.tsx`
- Dashboard is a server component with client `SessionRow` — wrap `SessionRow` list if needed

## Common Pitfalls

### Pitfall 1: RLS UPDATE Policies with `USING (true)`

**What goes wrong:** The `video_analyses` and `video_analysis_frames` tables have UPDATE policies with `USING (true)` and INSERT policies with `WITH CHECK (true)`. These were named "Service role can update/insert" but they apply to all authenticated users, not just the service role. The service role bypasses RLS entirely — so these policies actually apply to regular user tokens as well.

**Why it happens:** The intended pattern was "only the Inngest service role worker updates these rows." But because Supabase RLS policies apply to all clients (including user-scoped clients), `USING (true)` means any authenticated user can update any `video_analyses` row by calling the Supabase client directly.

**How to avoid:** Change `USING (true)` to `USING (video_id IN (SELECT id FROM videos WHERE coach_id = auth.uid()))` to match the SELECT policy.

**Warning signs:** Any `USING (true)` on a write policy in a table that should have ownership isolation.

**IMPORTANT context:** `src/app/api/analysis/route.ts` uses the service role client (`getServiceClient()`) for its DB writes, which bypasses RLS anyway. The user-scoped client (`createServerClient`) also runs the `video_analyses` UPDATE at line 92 of `usePoseAnalysis.ts` — this uses `createBrowserClient` which IS subject to RLS. So regular users CAN trigger the UPDATE with the current `USING (true)` policy, but they can only update with data the browser sends (not arbitrary data). The risk is low but should be corrected for principle of least privilege.

### Pitfall 2: `lg:overflow-hidden` on Flex Children

**What goes wrong:** `overflow-hidden` on a flex item prevents internal scroll. The pattern `flex flex-col lg:overflow-hidden` on the review page outer container is correct, but the `aside` with `lg:overflow-hidden` then has a child `div` with `overflow-y-auto` — this works only if the parent has a defined height (which it gets from `h-screen` on the outer container via `lg:h-screen`). On mobile where `flex-col min-h-screen` is used, the aside has no constrained height, so `overflow-y-auto` on the inner div is irrelevant — content just flows.

**Action needed:** Verify visually at 375px that the sidebar scrolls correctly below the video. The layout decision is "simple vertical scroll" — so the sidebar should render its full height and the user scrolls the page (not the sidebar) on mobile. This is already what happens with the current code.

### Pitfall 3: Next/Image CLS in Dashboard

**What goes wrong:** `Next/Image` requires explicit `width` and `height` or `fill` + a positioned container. `SessionRow` uses `width={80}` `height={56}` — but the CSS classes `w-full h-full` on the `<Image>` may cause CLS if the container renders before the image.

**Current code:**
```tsx
<Image src={thumbnailUrl} alt="Video thumbnail" width={80} height={56} className="w-full h-full object-cover" />
```
The container is `w-16 h-12 sm:w-20 sm:h-14` (fixed dimensions) — the image slot is pre-sized so CLS is minimal. However `w-full h-full` on an intrinsic-sized `Image` can cause paint issues. The safer pattern for thumbnail grids is `fill` with a relative positioned container.

### Pitfall 4: Middleware Rate Limit Map Memory Leak

**What goes wrong:** `rateLimitMap` grows unbounded if many IPs hit the server. A cleanup mechanism (delete expired entries) should run periodically.

**How to avoid:** Add a cleanup inside `checkRateLimit` — delete entries where `resetAt < Date.now()` when adding a new entry. Or use a periodic cleanup with `setInterval` (supported in Edge runtime but can be unpredictable in serverless). Simple approach: prune the map when its size exceeds a threshold (e.g., 10,000 entries).

### Pitfall 5: `supabase.auth.getUser()` in Review Page Uses Inline `createServerClient`

**What goes wrong:** `src/app/(app)/review/[videoId]/page.tsx` creates its own `createServerClient` inline instead of using `@/lib/supabase/server`. This is a pattern divergence that means changes to the server client config (e.g., adding logging) won't apply here. Not a security issue, but a maintainability issue.

**How to avoid:** Replace inline `createServerClient` with `import { createClient } from '@/lib/supabase/server'` — same as other page components.

### Pitfall 6: Worker Analysis Blocks Video Scrubbing

**What goes wrong:** `usePoseAnalysis.ts` seeks the video element (`video.currentTime = timestampS`) during analysis. If the user tries to scrub the video manually while analysis runs, the worker will fight the user for `currentTime` control. The `abortRef` mechanism handles cleanup on unmount but not mid-analysis user seeking.

**Assessment:** The MediaPipe analysis runs in a Web Worker (via Comlink), so CPU is off the main thread. The `seeked` event listener pattern is the correct approach. The user-facing smoothness concern is about video playback during analysis — since the worker is seeking frame-by-frame (not playing), the video won't "play" during analysis. This is expected behavior, not a bug. The "Re-analyze" button is disabled during analysis (correct). No fix needed for the worker itself — the concern is render performance during the result display loop.

## Open Questions

1. **Can the presign route ownership check be tightened?**
   - What we know: `presign/route.ts` validates auth but does NOT verify that `coachId` in the request body matches `user.id`. A coach could pass any `coachId` and create a video record under another coach's identity.
   - What's unclear: Is this exploitable? The `coach_id` in the `videos` INSERT is from the request body, not `user.id`.
   - Recommendation: FIX — replace `coachId: coachId` with `coach_id: user.id` (derive from auth, not body). This is a < 1 hour fix and a real security issue.

2. **What is the correct Vercel/Next.js rate limiting approach without Upstash?**
   - What we know: Next.js middleware runs in the Vercel Edge runtime. In-memory Maps work but reset per cold start. Vercel does not provide a built-in rate limiting primitive without Upstash or KV.
   - What's unclear: Does Vercel's Edge runtime guarantee same-instance routing for the same IP?
   - Recommendation: Use in-memory Map (per CONTEXT.md discretion). It handles single-user abuse (the primary concern) and requires zero new dependencies. Document the limitation.

3. **Does `video_analyses` INSERT policy `WITH CHECK (true)` allow anyone to insert?**
   - What we know: The policy is named "Service role can insert analyses" but applies to all authenticated users.
   - What's unclear: The application layer (Inngest transcoding function) uses the service role client to create the initial `video_analyses` row. Regular users never call the INSERT path. But the door is open.
   - Recommendation: Tighten to `WITH CHECK (video_id IN (SELECT id FROM videos WHERE coach_id = auth.uid()))` to match ownership.

## Performance Audit: Findings Summary

### Dashboard
- `SessionRow` fetches video status AND analysis summary per row — two queries per row, up to 10 rows = 20 queries/page load. Both use TanStack Query with `staleTime: Infinity` for analysis and conditional polling for status. This is N+1 at the React layer but each query is independent and cached. No server-side batching. Acceptable for 10 rows/page; note for Phase 3 if count grows.
- `Next/Image` with fixed container dims — CLS is minimal. No fix needed.
- No `next/font` or large font imports found — no font CLS risk.

### Upload Page
- UploadPageClient is client-only with simple state — no performance concerns.
- Mobile file input path is `md:hidden` — correct for 375px viewport.

### Review Page
- `usePoseAnalysis` seeks video frame-by-frame. Worker is off-thread (Comlink). No main-thread blocking.
- `VideoWithOverlay` draws skeleton on every `timeupdate` event — `timeupdate` fires ~4x/sec during playback, more during seek. Canvas operations are synchronous but lightweight (skeleton lines). No bottleneck observed in code.
- `AnalysisTimeline` renders a `div` per frame — potentially 25 frames × 5fps = 125 `div` elements for a 5-second video. Manageable.

### Worker Smoothness
- `runAnalysis` in `usePoseAnalysis.ts` updates state every 10 frames (`if (i % 10 === 0) setFrames([...collectedFrames])`). This triggers re-renders of `ReviewPageClient`, which re-computes `currentFrame`, `flaggedFrames`, `currentFlagIndex` via `useMemo`. At 10-frame batches this is ~5 re-renders per 5-second video. Acceptable.
