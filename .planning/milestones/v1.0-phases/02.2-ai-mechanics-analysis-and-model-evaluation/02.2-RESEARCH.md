## Summary

This phase requires three parallel streams of work: (1) qualitative evaluation of the existing MediaPipe analysis on real softball video, (2) model alternative research and prototyping, and (3) feature implementation — motion-type tagging in the upload flow and new mechanics flags in the analysis pipeline and sidebar UI.

The existing MediaPipe PoseLandmarker (full model, 33 landmarks, IMAGE mode) is documented to have specific limitations for sports use: limb orientation can flip on side-view angles, equipment (bats) confuses arm landmark detection, fast motion reduces tracking fidelity, and depth estimation is unstable. These are precisely the edge cases that softball batting and pitching produce. Developer evaluation should verify whether these limitations actually manifest on the project's softball clips before deciding on model changes.

The recommended prototyping strategy is: (A) keep MediaPipe as the baseline and layer Gemini 2.5 Flash (image analysis API) as a second opinion for qualitative description, and (B) prototype YOLO11-pose exported to ONNX for browser inference via onnxruntime-web as a potential drop-in replacement for the browser Web Worker. Gemini Flash has a free tier, making cost risk near-zero for this phase's evaluation. YOLO11 provides 17-keypoint COCO detection with 89.4% mAP@0.5, comparable accuracy with better documented sports performance.

**Primary recommendation:** Evaluate MediaPipe on real clips first. If skeleton quality is acceptable for the angles the app already uses (elbow slot, shoulder tilt, hip rotation), keep MediaPipe and layer new motion-specific flags on top. If evaluation reveals clear failures (limb flipping, lost tracking on bat-path frames), prototype YOLO11-ONNX in the browser worker as a replacement and Gemini Flash as a VLM overlay.

## Model Alternative Research

### Category 1: Off-the-Shelf Browser/Server Models

**MediaPipe PoseLandmarker (current)**
- 33 landmarks, IMAGE mode, GPU delegate with CPU fallback
- Evaluated validation sets: Yoga, Dance, HIIT — no sports-specific training
- Documented limitations for softball: limb-flip on side view, bat confuses arm landmarks, fast motion reduces fidelity, limited depth accuracy
- Source: [it-jim.com MediaPipe sports limitations](https://www.it-jim.com/blog/mediapipe-for-sports-apps/) — MEDIUM confidence

**YOLO11 Pose (recommended prototype candidate)**
- 17 COCO keypoints, 89.4% mAP@0.5 on COCO Keypoints dataset
- Released September 2024, production standard for 2025 per Roboflow
- Can be exported to ONNX format (`opset=12` for WebGPU compatibility) and run via `onnxruntime-web` in a browser Web Worker
- Existing GitHub project demonstrates YOLO11 multi-task ONNX in browser with WebGPU + WASM fallback
- Limitation: 17 keypoints (no dedicated wrist/ankle/foot splits) vs MediaPipe's 33; this means no left/right wrist isolation without post-processing
- Source: [Roboflow pose model comparison](https://blog.roboflow.com/best-pose-estimation-models/) — MEDIUM confidence (requires hands-on verification)

**MoveNet (Lightning / Thunder)**
- 17 keypoints, ~7ms (Lightning) / ~25-35ms (Thunder) inference on mobile CPU
- Accuracy on gait kinematics: comparable to OpenPose at joint level but optimized for speed not accuracy
- Runs via TensorFlow.js in browser
- NOT recommended for prototyping: less accurate than YOLO11 for sports, TF.js adds significant bundle weight
- Source: Roboflow comparison — MEDIUM confidence

**HRNet**
- 89.0% mAP@0.5 (close to YOLO11), high-resolution architecture
- Primarily server-side Python; no lightweight browser-ready version
- Overkill for this phase unless MediaPipe + YOLO11 both fail evaluation

### Category 2: Sports-Specific AI Models

**PitcherNet (University of Waterloo / Baltimore Orioles, 2024)**
- Analyzes pitcher kinematics from broadcast video: velocity, release point, pitch trajectory
- Research code presented at IEEE/CVF CVPR 2024
- Not publicly accessible as an API or installable package
- NOT prototypable in this phase — research only

**Automated pitching phase classification (2025 MDPI study)**
- 240fps slow-motion smartphone video of baseball pitchers
- 500 high school pitchers, 5-phase classification
- Academic research, no public API or npm package
- NOT prototypable in this phase — research only

**Driveline Baseball bat tracking (Dec 2024)**
- Proprietary bat-tracking computer vision
- No public API
- NOT prototypable

**Malter Analytics MLB OpenPose approach**
- Used OpenPose on MLB broadcast video to detect mechanics changes
- Server-side Python; no browser implementation
- Interesting approach for future: apply same concept with YOLO11

**Finding:** No production-ready, publicly-accessible sports-specific pose model exists for softball. The baseball-specific models are either research-only or proprietary. For this phase, the plan must use general-purpose models (MediaPipe or YOLO11) with softball-specific flag logic applied on top.

### Category 3: LLM/VLM-Based Analysis

**Gemini 2.5 Flash (recommended VLM prototype candidate)**
- Free tier: free image/video input (confirmed via official docs, Feb 2026)
- Paid tier: $0.30 per 1M tokens (images billed at ~560 tokens each → ~$0.000168/image)
- Supports sending a JPEG frame + text prompt → returns natural language mechanics description
- Can be called server-side from a Next.js API route or Inngest function
- API: `@google/genai` SDK, `gemini-2.5-flash` model, `generateContent()` with inline image data
- Limitation: Does NOT produce structured keypoints — outputs text description only; cannot replace the skeleton overlay
- Best use: augment MediaPipe with per-frame qualitative description ("pitcher's arm is behind the body at this frame") OR as standalone evaluation tool
- Source: [Gemini API pricing docs](https://ai.google.dev/gemini-api/docs/pricing) — HIGH confidence (official docs)

**GPT-4o Vision**
- ~$0.0015/image at standard resolution; more expensive than Gemini Flash for prototyping
- No compelling accuracy advantage for this use case vs Gemini
- Not recommended for prototyping given cost disadvantage

**VLM Architecture Decision:**
VLMs cannot produce the skeleton landmark data needed for overlay drawing. They are additive — they can describe what they see in a frame ("elbow is dropping at ball contact") but cannot replace the coordinate-based flag logic. The recommended use is: run MediaPipe (or YOLO11) for landmarks + angles, then optionally call Gemini Flash once per clip to get a holistic mechanics summary that supplements the per-frame flag data.

## Softball Mechanics: Top Coaching Flags

These are the mechanics issues softball coaches most commonly identify in video review, sourced from biomechanics literature and coaching resources.

### Batting Swing — Top 5 Coaching Flags (HIGH priority for new flags)

| Flag Name | Description | Detectable via Pose? | Landmarks Used |
|-----------|-------------|---------------------|----------------|
| Back Shoulder Drop | Back shoulder dips below contact plane; causes weak pop-ups and bat-path inefficiency | YES — shoulder tilt angle already computed | LEFT_SHOULDER, RIGHT_SHOULDER |
| Bat Casting / Arm Extension | Hands push away from body early; creates long looping swing, loses power | YES — elbow extension + wrist-to-hip distance | ELBOW, WRIST, HIP (same side) |
| Hip Load Failure | Batter fails to load weight onto back leg before stride; all arms, no hip power | PARTIAL — hip midpoint translation from stance to stride; hard without depth | LEFT_HIP, RIGHT_HIP |
| "Squishing the Bug" / Back Foot Spin | Back foot rotates on toes instead of driving through; indicates poor drive mechanics | LOW — foot landmarks (29-32) often have low visibility in single-camera video | LEFT_ANKLE (28), RIGHT_ANKLE (27) |
| Weight Transfer Lunge | Batter steps forward too early (lunge vs controlled stride); head drifts past front foot | PARTIAL — hip midpoint drift vs head (nose) lateral position | NOSE (0), HIP midpoint |

**Recommended new batting flag: Bat Casting (arm extension)**
- Most detectable with existing landmarks
- Compute: angle at elbow (shoulder-elbow-wrist) combined with distance of lead wrist from lead hip relative to body width
- Flag when wrist extends more than ~60% of shoulder-to-hip distance away from body prior to contact frame

### Windmill Pitching — Top 5 Coaching Flags (HIGH priority for new flags)

| Flag Name | Description | Detectable via Pose? | Landmarks Used |
|-----------|-------------|---------------------|----------------|
| Arm Circle Off-Plane / Arm Crossing Midline | Throwing arm crosses body's midline during backswing | YES — wrist X-position relative to shoulder midpoint during wind-up | RIGHT_WRIST relative to shoulder midpoint |
| Early Hip/Shoulder Rotation | Upper body opens toward home plate before stride lands; inhibits forward momentum transfer | YES — shoulder line angle during stride phase vs hip line angle | LEFT_SHOULDER, RIGHT_SHOULDER vs LEFT_HIP, RIGHT_HIP timing |
| Excessive Stride Length | Overly long stride limits trunk ROM through acceleration phase | PARTIAL — distance between stride foot and pivot foot at landing | ANKLE landmarks |
| Front Side Collapse | Excessive trunk/knee flexion at stride foot contact; disrupts kinetic chain | PARTIAL — hip and knee angle at stride landing | HIP, KNEE landmarks |
| Drive Knee Valgus | Back knee collapses inward during posterior weight shift | LOW — requires good knee landmark visibility from side angle | LEFT_KNEE or RIGHT_KNEE |

**Recommended new pitching flag: Arm-Shoulder Separation (premature rotation)**
- Most detectable with existing landmarks
- Compute: difference between shoulder tilt angle and hip angle at each frame during the acceleration phase (pre-contact frames)
- If shoulder line rotates toward target before hip line crosses threshold → "Premature Shoulder Opening" flag
- Source: PMC11969493 (2025 fastpitch pitching biomechanics guide) — MEDIUM confidence on threshold values

**Sources for biomechanics:**
- [PMC11969493 - Fastpitch Softball Pitching Biomechanics 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11969493/)
- [PMC8739590 - Softball Pitcher Shoulder Stress](https://pmc.ncbi.nlm.nih.gov/articles/PMC8739590/)
- [MVP Batting Cages - Softball Swing Mechanics](https://mvpbattingcages.com/softball-swing-mechanics/)

### Pattern 1: Motion-Type-Dispatched Flag Logic

**What:** A single `flagMechanics()` entry point that accepts `motionType` and delegates to motion-specific flag functions.

**When to use:** Keeps the usePoseAnalysis hook unchanged (it calls one function); flag logic stays separated by motion type.

```typescript
// src/lib/pose/flags.ts — extend existing pattern
export type MotionType = 'hitting' | 'pitching'

export function flagMechanics(
  elbowSlot: number | null,
  shoulderTilt: number | null,
  hipRotation: number | null,
  landmarks: NormalizedLandmark[],
  motionType: MotionType = 'hitting'  // default to hitting for backward compat
): MechanicsFlag[] {
  if (motionType === 'pitching') {
    return flagPitchingMechanics(elbowSlot, shoulderTilt, hipRotation, landmarks)
  }
  return flagHittingMechanics(elbowSlot, shoulderTilt, hipRotation, landmarks)
}
```

**Why:** Existing callers default to 'hitting'; no breaking change to the hook. Motion-specific logic stays cleanly separated.

### Pattern 2: Motion-Type Stored on videos Table, Passed Through Analysis Chain

**What:** `motion_type TEXT CHECK (motion_type IN ('hitting', 'pitching', 'unknown'))` column on `videos` table. The presign route writes it. The review page reads it from DB. The `usePoseAnalysis` hook receives it as a parameter.

```typescript
// Review page server component — fetch motion_type with video
```

**Why:** Single source of truth in DB. No re-tagging needed on re-analysis. Motion type is discoverable by future features without UI re-entry.

**Limitation:** YOLO11 outputs 17 COCO keypoints (not 33). Existing landmark index constants (`LANDMARK_INDICES`) reference MediaPipe's 33-point scheme. If YOLO11 replaces MediaPipe, all index references must map to COCO keypoints. This is a significant migration risk — only pursue if MediaPipe evaluation clearly fails.

### Anti-Patterns to Avoid

- **Hardcoding motion-type logic in the worker:** The worker runs in a sandboxed scope without access to DB or session state. Pass `motionType` as a parameter to the Comlink-exposed `detectOnImageBitmap` function, or better, pass it to the flag-computation step in the hook (which runs in main thread context).
- **Running VLM calls in the browser:** Gemini API key must stay server-side. Any Gemini integration must go through a Next.js API route or Inngest function.
- **Replacing MediaPipe without verifying YOLO11 keypoint schema:** YOLO11 17-point output requires a complete rewrite of `LANDMARK_INDICES` and all angle computation. Do not start this migration without a side-by-side prototype comparison first.
- **Adding `motionType` to `FrameAnalysis` on a per-frame basis:** Motion type is a video-level property; store it on the `videos` table, not repeated on every frame row.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| VLM image-to-text analysis | Custom frame description pipeline | `@google/genai` Gemini API | Handles tokenization, retry, safety filters, image encoding |
| ONNX model inference in browser | Raw WebAssembly ONNX runner | `onnxruntime-web` | Handles WebGPU backend, WASM fallback, tensor prep, output decoding |
| YOLO11 model export | Custom weight conversion | `ultralytics` Python CLI (`model.export(format='onnx')`) | Handles opset compatibility, quantization, input shape |
| Supabase migration | Raw SQL in app code | `supabase/migrations/006_*.sql` + `supabase db push` | Tracked, repeatable, CI-safe |
| JPEG frame extraction for VLM | Custom video → frame pipeline | `OffscreenCanvas` + `canvas.toDataURL('image/jpeg')` (already in codebase pattern) | Already established in `usePoseAnalysis` hook |

**Key insight:** The biomechanics logic (angle thresholds, flag conditions) IS domain-specific and should be hand-rolled — that is the core value. Only the model inference and API communication layers should use libraries.

## Common Pitfalls

### Pitfall 1: Motion Tag Not Propagating to Analysis
**What goes wrong:** `motionType` is captured in the upload UI but never reaches `flagMechanics()`. New motion-specific flags never trigger.
**Why it happens:** The data flows: UploadPageClient → VideoUploader → presign request → DB. Then separately: review page → usePoseAnalysis (reads video from DB but may not select `motion_type`).
**How to avoid:** Verify `motion_type` is in the `SELECT` on the review page server component and passed as a prop to `ReviewPageClient` → `usePoseAnalysis`.
**Warning signs:** Flags appear for wrong motion type, or new pitching flags appear on batting videos.

### Pitfall 2: YOLO11 Keypoint Index Mismatch
**What goes wrong:** Prototype loads YOLO11 output but applies MediaPipe's 33-point `LANDMARK_INDICES` constants, producing garbage angle values.
**Why it happens:** YOLO11 outputs 17 COCO keypoints in a different order/mapping than MediaPipe's 33.
**How to avoid:** Create a `YOLO_LANDMARK_INDICES` mapping that mirrors COCO keypoint assignments. Never mix index constants between models.
**Warning signs:** Elbow slot reads as 0° or 180° consistently; skeleton connects wrong joints.

### Pitfall 3: Gemini API Key in Browser Bundle
**What goes wrong:** `GEMINI_API_KEY` exposed in client-side JavaScript.
**Why it happens:** Accidentally importing Gemini SDK in a client component or worker.
**How to avoid:** Gemini calls must only occur in `src/app/api/**` server routes (no `NEXT_PUBLIC_` prefix on the env var).
**Warning signs:** Network tab in browser shows request directly to `generativelanguage.googleapis.com`.

### Pitfall 4: New Flags Not Visible in MechanicsSidebar
**What goes wrong:** New flags fire in `flagMechanics()` but don't appear in the UI.
**Why it happens:** `MechanicsSidebar` renders `currentFrame.flags` which comes from stored DB data. If re-analysis isn't triggered after flag logic changes, old flag data persists.
**How to avoid:** After updating flag logic, trigger re-analysis on a test video. Verify `video_analysis_frames.flags` JSONB in DB contains the new flag before checking the UI.
**Warning signs:** Flags appear in console log but not in sidebar; sidebar shows "No mechanics issues" on clearly flawed frames.

### Pitfall 5: Pitching-Specific Flag Applied to Batting Videos
**What goes wrong:** "Premature Shoulder Opening" flag fires on all videos (batting and pitching) because `motionType` defaults to a wrong value.
**Why it happens:** DB column is NULL for videos uploaded before the migration; code treats NULL as 'hitting' but logic is inverted.
**How to avoid:** Set `DEFAULT 'unknown'` on `motion_type` column; in `flagMechanics()`, treat `'unknown'` the same as `'hitting'` for backward compat. Document the default clearly.

### Pitfall 6: MediaPipe Bat Interference on Contact Frame
**What goes wrong:** On the exact frame where bat-ball contact occurs, the bat shaft creates a false landmark between wrist and elbow. Elbow slot reads wildly wrong at precisely the most important frame.
**Why it happens:** MediaPipe was not trained on images with sporting equipment. The bat appears as a limb extension.
**How to avoid:** Consider excluding the contact frame (marked with `isContact: true`) from angle computations that involve arm landmarks, or applying a rolling median filter on angle values across adjacent frames to smooth out single-frame spikes.
**Warning signs:** Elbow slot angle on the `isContact` frame is >150° or <30° while adjacent frames are in normal range.

### Pitfall 7: VideoUploader Not Passing motionType to Presign
**What goes wrong:** `motionType` state lives in `UploadPageClient` but `VideoUploader` has its own `uploadFile` callback that constructs the presign body.
**Why it happens:** The selector is a sibling of `VideoUploader`, not a parent prop.
**How to avoid:** Pass `motionType` as a prop to `VideoUploader` (similar to how `athleteId` and `coachId` are passed). Update the `VideoUploaderProps` interface.
**Warning signs:** Presign request body logs show `motionType: undefined`.

### Motion-Specific Flag Dispatch in flags.ts

```typescript
// src/lib/pose/flags.ts — extend flagMechanics signature
export function flagMechanics(
  elbowSlot: number | null,
  shoulderTilt: number | null,
  hipRotation: number | null,
  landmarks: NormalizedLandmark[],
  motionType: MotionType = 'hitting'
): MechanicsFlag[] {
  const baseFlags = flagCommonMechanics(elbowSlot, shoulderTilt, landmarks)
  if (motionType === 'pitching') {
    return [...baseFlags, ...flagPitchingSpecific(shoulderTilt, hipRotation, landmarks)]
  }
  return [...baseFlags, ...flagHittingSpecific(elbowSlot, hipRotation, landmarks)]
}
```

```typescript
// Bat Casting detection: lead wrist extends too far from body before contact
// Uses lead side landmarks (RHH = right-handed hitter, uses left wrist/hip as lead)
function detectBatCasting(landmarks: NormalizedLandmark[]): MechanicsFlag[] {
  const leadWrist = landmarks[LANDMARK_INDICES.LEFT_WRIST]   // 15 for RHH
  const leadHip = landmarks[LANDMARK_INDICES.LEFT_HIP]       // 23 for RHH
  const leftShoulder = landmarks[LANDMARK_INDICES.LEFT_SHOULDER]  // 11
  const rightShoulder = landmarks[LANDMARK_INDICES.RIGHT_SHOULDER]  // 12

  if (!leadWrist || !leadHip || !leftShoulder || !rightShoulder) return []
  if (leadWrist.visibility < FLAG_CONFIDENCE_THRESHOLD) return []
  if (leadHip.visibility < FLAG_CONFIDENCE_THRESHOLD) return []

  const shoulderWidth = Math.abs(rightShoulder.x - leftShoulder.x)
  const wristDistFromHip = Math.abs(leadWrist.x - leadHip.x)

  // Flag if wrist is more than 0.6 shoulder-widths away from lead hip (normalized)
  // Threshold is developer-tunable; validate against real footage
  if (shoulderWidth > 0 && wristDistFromHip / shoulderWidth > 0.6) {
    const conf = (leadWrist.visibility + leadHip.visibility) / 2
    return [{ issue: 'Bat Casting', confidence: conf, severity: 'warning',
              jointIndices: [LANDMARK_INDICES.LEFT_WRIST, LANDMARK_INDICES.LEFT_ELBOW] }]
  }
  return []
}
```

### Pitching: Premature Shoulder Opening Flag (new)

```typescript
// Premature Shoulder Opening: shoulder line rotates toward home plate before
// hip rotation reaches threshold — disrupts kinetic chain sequencing
// Source: PMC11969493 - Fastpitch Softball Pitching Biomechanics 2025
function detectPrematureShoulderOpening(
  shoulderTilt: number | null,
  hipRotation: number | null,
): MechanicsFlag[] {
  if (shoulderTilt === null || hipRotation === null) return []

  // During pitching wind-up/stride, hips should lead shoulders.
  // If shoulder opens (low shoulderTilt abs value = level/open) while hips still loading
  // (hipRotation near 0 = square to plate), premature opening is occurring.
  // These thresholds are LOW confidence — validate against real pitching footage.
  const shoulderOpen = Math.abs(shoulderTilt) < 10  // nearly level = facing batter
  const hipsStillLoading = Math.abs(hipRotation) < 30  // still square to plate

  if (shoulderOpen && hipsStillLoading) {
    return [{
      issue: 'Premature Shoulder Opening',
      confidence: 0.75,  // Proxy — no per-landmark conf in this version
      severity: 'warning',
      jointIndices: [LANDMARK_INDICES.LEFT_SHOULDER, LANDMARK_INDICES.RIGHT_SHOULDER],
    }]
  }
  return []
}
```

**NOTE:** The thresholds in both examples above are LOW confidence. They are starting points for developer evaluation against real footage. The CONTEXT.md decision allows Claude's discretion on exact thresholds — these should be refined during the qualitative evaluation step.

```typescript
// src/app/api/analysis/vlm-eval/route.ts (prototype only)
import { GoogleGenerativeAI } from '@google/genai'

const genai = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!)

    { inlineData: { mimeType: 'image/jpeg', data: base64Frame } },
    prompt,
  ])
  return Response.json({ description: result.response.text() })
}
```

## Open Questions

1. **MediaPipe evaluation outcome unknown until developer runs it**
   - What we know: MediaPipe has documented limitations for sports (side-angle limb flipping, equipment interference)
   - What's unclear: Whether these limitations manifest on the specific softball clips in the project, or whether the existing skeleton quality is "good enough"
   - Recommendation: Do not decide on model replacement until evaluation is complete. The code changes for new flags and motion-type tagging are independent and should proceed regardless.

2. **Pitching flag thresholds are LOW confidence**
   - What we know: PMC11969493 describes biomechanical phases and error patterns; landmarks are identifiable
   - What's unclear: The exact angle values at which "premature shoulder opening" becomes a problem vary by pitcher height, arm speed, and style
   - Recommendation: Start with wide, conservative thresholds (flag only obvious outliers) and refine based on developer evaluation against real pitching footage

3. **Bat casting flag — handedness assumption**
   - What we know: The existing `computeElbowSlot` already supports handedness ('right' | 'left') but defaults to right-handed
   - What's unclear: Upload flow has no handedness selector; how should the system handle left-handed batters?
   - Recommendation: For this phase, hardcode to right-handed (same as existing behavior, flag.ts comment already notes this). Left-handed support is a future enhancement. Document this limitation clearly in the sidebar.

4. **Gemini API key availability**
   - What we know: Gemini 2.5 Flash has a free tier for development
   - What's unclear: Whether the project environment has a `GEMINI_API_KEY` env var or if one needs to be obtained from console.cloud.google.com
   - Recommendation: Add `GEMINI_API_KEY` to `.env.local.example` as a required var for the VLM prototype. Developer must provision a key from [Google AI Studio](https://aistudio.google.com) before Wave 3.

## Evaluation Results

**Evaluated:** 2026-03-01
**Clips tested:** Real batting clip (hitting motion) and real pitching clip (pitching motion), both under 5 seconds

### EVAL-01: MediaPipe Evaluation

**Result: PASS**

Skeleton overlay lands correctly on the body for both motion types. Key angles — elbow, hip, and shoulder — read approximately right for both the hitting and pitching clips. No limb flipping or landmark confusion observed. MediaPipe quality is sufficient for the flag logic and angle visualizations the app already relies on. No model replacement is warranted.

### EVAL-02a: Gemini 2.5 Flash VLM Evaluation

**Result: Adds value as overlay layer**

Tested on batting and pitching frames via the POST /api/analysis/vlm-eval prototype route. Gemini produces useful 2-3 sentence mechanics descriptions that complement the quantitative flags from MediaPipe. The descriptions are specific about body part issues and readable by coaches. This makes Gemini a viable optional VLM commentary overlay — not a replacement for the skeleton, but a qualitative supplement that can surface issues the angle thresholds may miss.

### EVAL-02b: YOLO11-pose ONNX Evaluation

**Result: Skipped — not available for local testing**

The `yolo11n-pose.onnx` model file was not available for local testing. The browser worker prototype (`src/workers/yolo-pose.worker.ts`) was written and compiles correctly, but could not be run end-to-end without the model file. Key finding documented for future reference: YOLO11 uses 17 COCO keypoints (different order and count from MediaPipe's 33), so any future migration would require a full rewrite of `LANDMARK_INDICES` and all angle computation functions. Investigation is deferred.

**Keypoint schema difference (for future reference):**
- MediaPipe: 33 keypoints, custom order (0=nose, 11=left_shoulder, 12=right_shoulder, 13=left_elbow, ...)
- YOLO11 COCO: 17 keypoints (0=nose, 5=left_shoulder, 6=right_shoulder, 7=left_elbow, ...)
- Never apply MediaPipe `LANDMARK_INDICES` to YOLO11 output — garbage angle values will result

### EVAL-03: Decision

**Keep MediaPipe as primary pose estimator + add new motion-specific flags.**

**Layer Gemini 2.5 Flash as optional VLM commentary overlay** — adds qualitative coach-readable descriptions that supplement quantitative flags; prototype confirmed value.

**YOLO11 investigation deferred** — model file not available for local testing; no evidence that MediaPipe quality requires replacement at this stage; revisit if angle accuracy issues emerge in future phases.

**Rationale:** MediaPipe passes the CONTEXT.md evaluation bar. The investment to migrate to YOLO11 (full landmark index rewrite, new worker, revalidation of all angle thresholds) is not justified when MediaPipe is performing correctly. The correct next step is to improve flag quality and add motion-specific flags on top of the working MediaPipe foundation.
