# Phase 2.2: AI Mechanics Analysis and Model Evaluation - Context

**Gathered:** 2026-02-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Evaluate the current MediaPipe-based mechanics analysis on real softball video (both batting swing and windmill pitch), research and prototype alternative AI models, improve mechanics flag quality, add motion-type tagging to the upload flow, and surface at least one new mechanic per motion type in the review page UI. Produces working code improvements plus a written evaluation report.

Annotation tools, feedback delivery to athletes, and session history are separate phases.

</domain>

<decisions>
## Implementation Decisions

### Evaluation Methodology
- Evaluation is qualitative: developer watches analysis on real softball video and judges if the skeleton lands correctly and flags make sense
- Pass bar: skeleton mostly correct on the body, key angles (elbow, hip, shoulder) look approximately right
- No formal ground-truth measurements or quantitative scoring needed for this phase
- If analysis is clearly wrong → research and prototype alternative models (not just tune MediaPipe thresholds)

### Motion Coverage
- Evaluate against both motions: **batting swing** and **windmill pitching**
- All existing flags (dropping elbow, early hip rotation, shoulder tilt, hip rotation angle) are evaluated for both motions
- Research agent should identify the top 3-5 mechanics issues softball coaches most commonly flag in video review — these become targets for new flag additions
- At minimum, one new well-functioning mechanics flag per motion type must be added by end of phase

### Motion-Type Tagging
- Upload flow must include a **hitting / pitching** selector (coach or athlete tags motion type at upload time)
- Analysis pipeline uses the motion tag to apply motion-specific flag logic
- This UI change is in scope for Phase 2.2, not deferred

### Model Alternatives Research
- Research all three categories:
  1. Off-the-shelf browser/server models (MoveNet, BlazePose, MMPose, etc.)
  2. Sports-specific AI models trained on athletic motion
  3. LLM/VLM-based analysis (GPT-4V, Gemini Vision, or similar — describe mechanics from frames without pose model)
- Constraints: **server-side inference is acceptable** (Inngest job or API route); **external API calls are acceptable** (cost must be reasonable)
- Browser-only is NOT a hard requirement — architecture can change if accuracy is meaningfully better
- Prototype the top 2 candidates by running them on a sample softball frame and comparing skeleton quality visually
- Deliverable: comparison of prototyped candidates → developer picks the winner

### Phase Deliverable
- **Working code** improvements to mechanics analysis integrated into the existing pipeline
- **New mechanics flags visible in MechanicsSidebar** on the review page — coaches see improvements without dev tools
- **Motion-type tag** on upload UI wired to motion-specific analysis rules
- **Written evaluation summary** captured as a research/analysis document (can be RESEARCH.md)
- Phase is NOT complete unless new flags show up in the UI and the motion tag is functional end-to-end

### Claude's Discretion
- Which specific alternative models to prototype (from within the three categories above)
- Exact flag logic and angle thresholds for newly added mechanics
- Whether to replace MediaPipe entirely or layer a second model alongside it
- UI treatment of the hitting/pitching selector on the upload page

</decisions>

<specifics>
## Specific Ideas

- Researcher should identify "top softball coaching flags" from real coaching resources — not invent mechanics rules
- For prototyping: extract a frame from a real softball clip, run each candidate, compare visually — not a full pipeline swap
- The evaluation process itself (run analysis, watch output, judge quality) should happen as part of this phase — not just research

</specifics>

<deferred>
## Deferred Ideas

- Motion auto-detection (no manual tag) — if the phase proves motion-specific analysis adds value, auto-detection is a future enhancement
- Benchmarked multi-frame evaluation with quantitative scoring — too much overhead for this phase
- Full pipeline swap to a new model architecture — only warranted if prototyping reveals MediaPipe is clearly unsuitable; otherwise improve incrementally
- Drill recommendations linked to flagged mechanics (AI-05 in v2 requirements)
- Progress tracking across sessions (PROG-01, PROG-02 in v2 requirements)

</deferred>
