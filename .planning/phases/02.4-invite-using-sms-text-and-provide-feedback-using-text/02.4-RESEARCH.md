# Phase 02.4: Invite Using SMS Text and Provide Feedback Using Text — Research

**Researched:** 2026-03-02
**Domain:** SMS delivery (Twilio), athlete invite flow extension, coach feedback delivery via text
**Confidence:** HIGH for standard stack and integration patterns; MEDIUM for compliance specifics

---

## Summary

Phase 02.4 adds two SMS-powered capabilities to the existing coach-athlete workflow: (1) the coach can invite an athlete by entering their phone number instead of (or in addition to) their email, sending a Twilio SMS with the magic-link URL; and (2) after reviewing a video, the coach can send an SMS feedback summary directly to the athlete's phone number.

The existing `inviteAthlete` server action in `src/actions/auth.ts` already handles email-based invite via `admin.auth.admin.inviteUserByEmail`. Phase 02.4 extends this by adding an optional `phone` field to the invite modal and to `coach_athletes`, then wiring a new `sendSms` helper that calls the Twilio API. The feedback-via-text flow follows the same helper: the coach clicks "Send feedback via text" on the review page, which calls a server action that assembles a short summary and calls Twilio.

Twilio is the correct library choice. At `^5.11.2` it ships built-in TypeScript types and is the dominant Node.js SMS SDK. The alternative (Supabase phone auth) solves a different problem (phone-based login, not custom outbound SMS), and is not appropriate here.

**Primary recommendation:** Add Twilio `^5.x` to the project; add an `athlete_phone` column to `coach_athletes`; extend `InviteAthleteModal` with an optional phone field; add a `sendSms()` server utility; add a "Send feedback via text" button to the review page.

### Pattern 1: Twilio SMS Utility (lib/sms.ts)

**What:** A single server-side helper that initializes the Twilio client once and exports `sendSms()`.
**When to use:** Called from any server action that needs to send an outbound SMS.

```typescript
// src/lib/sms.ts
// Source: https://www.twilio.com/en-us/blog/send-sms-typescript-twilio
import { Twilio } from 'twilio'

function getTwilioClient() {
  const accountSid = process.env.TWILIO_ACCOUNT_SID
  const authToken = process.env.TWILIO_AUTH_TOKEN
  if (!accountSid || !authToken) {
    throw new Error('Missing Twilio credentials')
  }
  return new Twilio(accountSid, authToken)
}

export async function sendSms(to: string, body: string): Promise<string> {
  const client = getTwilioClient()
  const message = await client.messages.create({
    from: process.env.TWILIO_PHONE_NUMBER!,
    to,
    body,
  })
  return message.sid
}
```

**Key constraint:** `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_PHONE_NUMBER` must NOT have `NEXT_PUBLIC_` prefix. Server-side only (same pattern as `GEMINI_API_KEY` in Phase 02.2).

### Pattern 2: Extending `inviteAthlete()` for Phone

**What:** The existing `inviteAthlete(email, coachId)` server action adds an optional `phone?: string` parameter. When provided, after sending the email invite, a follow-up SMS is sent containing the magic link URL.

```typescript
// src/actions/auth.ts — extend signature
export async function inviteAthlete(
  email: string,
  coachId: string,
  phone?: string  // E.164 format e.g. +14155552671
): Promise<{ success: true; userId: string | undefined } | { error: string }>
```

When `phone` is provided:
1. Run existing email invite logic (unchanged)
2. Persist `athlete_phone` to `coach_athletes` row
3. Call `sendSms(phone, inviteText)` where `inviteText` includes the magic link

The magic link URL is: `${process.env.NEXT_PUBLIC_APP_URL}/invite/accept`

Note: The Supabase invite email flow sends the user through `/auth/callback`, which sets the session and redirects to `/invite/accept`. The SMS message should contain the same `${NEXT_PUBLIC_APP_URL}/auth/callback` redirect URL format that email currently uses, or a simpler public URL with instructions.

### Pattern 3: Feedback SMS Server Action

**What:** A new `sendFeedbackSms()` server action that reads athlete phone number from `coach_athletes`, assembles a short text summary from the video analysis, and calls `sendSms()`.

```typescript
// src/actions/feedback.ts (new file)
'use server'

import { createClient } from '@/lib/supabase/server'
import { sendSms } from '@/lib/sms'

export async function sendFeedbackSms(videoId: string): Promise<{ success: true } | { error: string }> {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { error: 'Not authenticated' }

  // Fetch video with athlete phone
  const { data: video } = await supabase
    .from('videos')
    .select('athlete_id, videos_analyses(vlm_summary)')
    .eq('id', videoId)
    .eq('coach_id', user.id)
    .maybeSingle()

  if (!video) return { error: 'Video not found' }

  // Get athlete phone from coach_athletes
  const { data: roster } = await supabase
    .from('coach_athletes')
    .select('athlete_phone')
    .eq('coach_id', user.id)
    .eq('athlete_id', video.athlete_id)
    .maybeSingle()

  if (!roster?.athlete_phone) return { error: 'No phone number on file for this athlete' }

  const summary = (video as any).video_analyses?.vlm_summary ?? 'Your coach has reviewed your video.'
  const body = `Mechanics feedback from your coach:\n\n${summary}\n\nView full analysis: ${process.env.NEXT_PUBLIC_APP_URL}/submissions`

  await sendSms(roster.athlete_phone, body)
  return { success: true }
}
```

### Pattern 4: Phone Field in InviteAthleteModal

**What:** Extend the existing `InviteAthleteModal` with an optional phone input. The form sends both email and phone to the updated `inviteAthlete()` action.

```typescript
// Addition to InviteAthleteModal.tsx
const [phone, setPhone] = useState('')

// In form submit handler:
const result = await inviteAthlete(email, coachId, phone || undefined)
```

UI note: Phone input should use `type="tel"` with a placeholder like `+1 (555) 000-0000 (optional)`. Do not make phone required — the email-only invite path must continue to work.

### Anti-Patterns to Avoid

- **Storing phone without E.164 normalization:** Numbers like `(555) 555-1234` or `555-555-1234` will fail Twilio validation. Validate or normalize to `+1XXXXXXXXXX` before storing and before calling `sendSms()`. Use a simple check: value must start with `+` and contain 7-15 digits.
- **Using `NEXT_PUBLIC_` prefix for Twilio credentials:** These credentials must stay server-side only. Exposing them in the browser bundle is a critical security issue.
- **Sending feedback SMS inline in a server component render:** Call `sendFeedbackSms` only from a form action or button click event, never during page load. Twilio is a third-party call that can fail or be slow.
- **Sending unsolicited SMS to athletes who did not provide a phone:** Phone input must be clearly optional, and SMS should only be sent when `athlete_phone` is on file.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Outbound SMS | Custom HTTP to Twilio REST | `twilio` npm package | Handles auth, retries, error codes, TypeScript types |
| Phone number validation | Custom regex | Twilio E.164 format check (`/^\+[1-9]\d{1,14}$/`) or `libphonenumber-js` | Phone number formats are deceptively complex across country codes |

**Key insight:** Twilio already handles message queuing, delivery status, and carrier routing. Do not try to implement retry logic for SMS — if `client.messages.create()` rejects, surface the error to the user and let them retry manually.

## Common Pitfalls

### Pitfall 1: Twilio Trial Account Restrictions
**What goes wrong:** Twilio free trial accounts can only send SMS to verified phone numbers. During development/testing, every test phone number must be manually verified in the Twilio console.
**Why it happens:** Trial accounts are restricted by Twilio to prevent abuse.
**How to avoid:** Verify test numbers in Twilio console immediately. For integration testing in CI, mock the `sendSms()` helper or use Twilio's test credentials (`+15005550006` as sender, no real delivery).
**Warning signs:** `21608 - The number is unverified` error from Twilio API.

### Pitfall 2: A2P 10DLC Registration Requirement
**What goes wrong:** US carriers now require all application-to-person (A2P) SMS to be registered under 10DLC. Unregistered traffic may be filtered or blocked.
**Why it happens:** FCC mandated A2P 10DLC in 2023; carrier enforcement became strict.
**How to avoid:** Register a Sole Proprietor Brand in Twilio Console (one-time $4.50 fee for individuals). Campaign review takes 10-15 business days. Sole Proprietor cap is ~1,000 message segments/day to T-Mobile (~3,000 across all US carriers) — sufficient for this use case.
**Warning signs:** Messages delivered with "Sent from a Twilio Trial account" prefix (trial mode), or silent delivery failures on certain carriers.

### Pitfall 3: SMS Character Limit Truncation
**What goes wrong:** A VLM feedback summary can easily exceed 160 characters (one SMS segment). Multi-segment messages (up to 1,600 characters) are supported but cost more per segment (each 153 characters over 160 is a new segment).
**Why it happens:** GSM-7 encoding allows 160 chars in a single SMS; exceeding this splits into concatenated segments.
**How to avoid:** Truncate the summary to 300 characters max in the feedback SMS body (Twilio sends up to ~2 segments). Alternatively, send a short teaser + link to the full review.
**Warning signs:** Message costs doubling due to multi-segment sends.

### Pitfall 4: Phone Number Not In E.164 Format
**What goes wrong:** Twilio rejects `to` numbers that are not in E.164 format (`+[country code][number]`). User input like `555-123-4567` will cause a Twilio API error.
**Why it happens:** Twilio's API requires E.164 strictly.
**How to avoid:** Validate input on the client with a simple regex `/^\+[1-9]\d{1,14}$/` before form submission. Show an inline error if the format is wrong.
**Warning signs:** Twilio error code `21211 — Invalid 'To' Phone Number`.

### Pitfall 5: TCPA Compliance for Outbound SMS
**What goes wrong:** Sending unsolicited SMS to users who did not opt in can violate the Telephone Consumer Protection Act (TCPA). Fines are $500-$1,500 per message.
**Why it happens:** TCPA applies to automated outbound messages.
**How to avoid:** Phone number collection occurs only when the coach explicitly enters the athlete's number with the athlete's knowledge, and the invite SMS is a transactional notification (not marketing). Include "Reply STOP to opt out" in the invite SMS body. Keep the feedback SMS to service/transactional content only (analysis results, not promotional). Store phone numbers only when athlete provides consent.
**Warning signs:** None at dev time — this is a legal/operational risk that appears at production scale.

### Pitfall 6: Inngest Not Required for Simple SMS
**What goes wrong:** Over-engineering SMS delivery as an Inngest background job adds complexity without benefit at this scale.
**Why it happens:** The project already uses Inngest for transcoding, which runs long.
**How to avoid:** Call `sendSms()` directly from server actions (synchronous, < 1 second). Inngest wrapping is only worthwhile if: (a) sending bulk SMS to many athletes at once, (b) requiring retry-with-delay logic, or (c) delivery status webhooks are needed. None of these apply to Phase 02.4.
**Warning signs:** Unnecessary queue latency on what should be an instant action.

## Open Questions

1. **Should invite SMS replace or supplement email invite?**
   - What we know: Current flow sends an email magic link via `inviteUserByEmail`. The Supabase auth session flow depends on email links (hash fragment tokens).
   - What's unclear: If athlete receives SMS with a magic link URL, Supabase still handles auth via email. The SMS link must point to the same `/auth/callback` URL that the email link uses. The invite SMS is supplementary (a text message pointing to the link), not a replacement for email auth.
   - Recommendation: Keep email as the required primary invite channel. SMS is additive — when a phone number is provided, send an SMS alongside the email. Do not require phone for invite.

2. **Where does the "Send feedback via text" button live?**
   - What we know: The review page has `MechanicsSidebar` with AI flags and VLM commentary.
   - What's unclear: Should feedback SMS go in `MechanicsSidebar` (near VLM summary), or as a dedicated action in a new "Feedback" panel?
   - Recommendation: Add it to `MechanicsSidebar` near the Session Summary / VLM commentary section, since that's the natural source of the feedback content. Disable the button with a tooltip if `athlete_phone` is null.

3. **What content goes in the feedback SMS?**
   - What we know: `vlm_summary` (from Phase 02.3) is stored in `video_analyses`. It is a Gemini Flash-generated text summary.
   - What's unclear: VLM summary may be long. SMS has a practical 320-character soft limit.
   - Recommendation: Truncate `vlm_summary` to 280 characters, append a link to `/submissions`, keep total under 320 characters to stay within 2 SMS segments.

4. **A2P 10DLC registration timing**
   - What we know: Sole Proprietor Brand registration takes 10-15 business days and costs $4.50 once.
   - What's unclear: When will this app go to production? Trial mode is sufficient for development.
   - Recommendation: Document the registration requirement in `.env.local.example` and in a code comment on `sendSms()`. Do not block Phase 02.4 implementation on registration completion.
