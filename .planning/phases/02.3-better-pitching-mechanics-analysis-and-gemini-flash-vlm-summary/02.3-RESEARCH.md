Phase 02.3 has three independent implementation tracks that can be built in parallel: (1) two new pitching mechanics flags in `flags.ts`, (2) pitching-specific ideal ranges and sidebar label renaming, and (3) Gemini Flash VLM commentary wired into the Session Summary UI with DB persistence.

The contact frame extraction is the trickiest integration point: `AnalysisSummary.tsx` currently receives `SummaryFrame[]` (no `isContact` field), so the interface must be extended or the contact frame must be passed separately.

Biomechanics research reveals that specific numerical elbow-angle thresholds for the windmill arm circle are **not authoritatively defined** in literature — the studies focus on qualitative mechanics principles rather than prescriptive ranges. Claude has full discretion on the exact threshold for Arm Circle (Bent Elbow). **Primary recommendation:** Build the three tracks as three discrete plans with minimal cross-dependencies: Plan 01 (new flags + pitching ideal ranges), Plan 02 (sidebar label rename), Plan 03 (Gemini VLM commentary + DB persistence). Plan 03 is the most complex due to the contact frame extraction and DB wiring.

### Pattern 1: New Flag Detector Functions

**What:** Pure function taking `NormalizedLandmark[]` → returning `MechanicsFlag[]`. Same structure as existing `detectBatCasting()` and `detectPrematureShoulderOpening()`.

**When to use:** Every new mechanics flag gets its own isolated detect function, then is called from the motion-specific dispatcher (`flagPitchingMechanics`).

**Example (following existing pattern in flags.ts):**
```typescript
// Source: flags.ts — detectBatCasting() and detectPrematureShoulderOpening() patterns
function detectArmCircleBentElbow(
  landmarks: NormalizedLandmark[],
  isWindUpPhase: boolean  // derived from frame position relative to contact frame
): MechanicsFlag[] {
  const shoulder = landmarks[LANDMARK_INDICES.RIGHT_SHOULDER]  // index 12
  const elbow    = landmarks[LANDMARK_INDICES.RIGHT_ELBOW]     // index 14
  const wrist    = landmarks[LANDMARK_INDICES.RIGHT_WRIST]     // index 16

  if (!shoulder || !elbow || !wrist) return []
  if (shoulder.visibility < FLAG_CONFIDENCE_THRESHOLD) return []
  if (elbow.visibility < FLAG_CONFIDENCE_THRESHOLD) return []
  if (wrist.visibility < FLAG_CONFIDENCE_THRESHOLD) return []

  // Compute elbow angle (shoulder-elbow-wrist)
  const elbowAngle = computeAngleDeg(shoulder, elbow, wrist)
  const BENT_THRESHOLD = 130  // Claude's discretion — elbow should be near-extended (>140°) during wind-up

  if (isWindUpPhase && elbowAngle < BENT_THRESHOLD) {
    const conf = (shoulder.visibility + elbow.visibility + wrist.visibility) / 3
    return [{
      issue: 'Arm Circle (Bent Elbow)',
      confidence: conf,
      severity: 'warning',
      jointIndices: [LANDMARK_INDICES.RIGHT_ELBOW],
    }]
  }
  return []
}
```

### Pattern 2: Stride Off Power Line Detection

**What:** Detect whether the stride foot (LEFT_ANKLE for RHP) lands significantly off the hip-line (the vertical axis defined by the pitcher's hip X-coordinate at wind-up).

**Key MediaPipe landmarks for this flag:**
- `LEFT_ANKLE` (index 27) = stride foot for a right-handed pitcher (RHP strides toward 3rd-base side with left foot)
- `RIGHT_ANKLE` (index 28) = drive foot / pivot foot
- `LEFT_HIP` (index 23) + `RIGHT_HIP` (index 24) = define the hip midline

**Research-backed reference value:** PMC11542118 (2024) measured stride-foot deviation as ±0.2m normalized for collegiate pitchers. In MediaPipe normalized coordinates (0–1 range), 0.2m corresponds to roughly 0.10–0.15 of frame width depending on camera distance. A threshold of 0.15 normalized units is a reasonable starting point.

**Example:**
```typescript
function detectStrideOffPowerLine(landmarks: NormalizedLandmark[]): MechanicsFlag[] {
  const strideAnkle = landmarks[LANDMARK_INDICES.LEFT_ANKLE]  // index 27 — stride foot for RHP
  const driveAnkle  = landmarks[LANDMARK_INDICES.RIGHT_ANKLE] // index 28 — pivot foot
  const leftHip  = landmarks[LANDMARK_INDICES.LEFT_HIP]       // index 23
  const rightHip = landmarks[LANDMARK_INDICES.RIGHT_HIP]      // index 24

  if (!strideAnkle || !driveAnkle || !leftHip || !rightHip) return []
  if (strideAnkle.visibility < FLAG_CONFIDENCE_THRESHOLD) return []
  if (driveAnkle.visibility < FLAG_CONFIDENCE_THRESHOLD) return []

  // Power line = the X-axis position of the drive ankle (home plate direction)
  const powerLineX = driveAnkle.x
  const lateralOffset = strideAnkle.x - powerLineX

  const STRIDE_OFFSET_THRESHOLD = 0.15  // Claude's discretion — normalized units
  if (Math.abs(lateralOffset) > STRIDE_OFFSET_THRESHOLD) {
    const conf = (strideAnkle.visibility + driveAnkle.visibility) / 2
    const direction = lateralOffset > 0 ? 'open' : 'closed'
    return [{
      issue: `Stride Off Power Line (${direction})`,
      confidence: conf,
      severity: 'warning',
      jointIndices: [LANDMARK_INDICES.LEFT_ANKLE, LANDMARK_INDICES.RIGHT_ANKLE],
    }]
  }
  return []
}
```

**Caveat (MEDIUM confidence):** The normalized x-axis in MediaPipe is the horizontal direction in the image frame. For a side-view camera (which this app requires per framing check), the power line runs perpendicular to the camera view — it is the z-axis in world coordinates, NOT the x-axis. From a side-view perspective, detecting stride position requires using the **y-axis** (vertical in image, but represents depth in the real world when pitcher is facing camera). This is a fundamental limitation. For a front-facing camera, x-axis works. For a side-view camera, stride detection is unreliable in 2D normalized coordinates.

**Implication for planner:** The stride off power line flag should be implemented with a conservative threshold and marked as experimental/low-confidence when emitted, OR the detection should use world landmarks (z-coordinates) if available from MediaPipe PoseLandmarker. The current `NormalizedLandmark` type only stores `x, y, z, visibility` — `z` from MediaPipe's normalized landmark is a depth estimate relative to the hip midpoint, which COULD work for stride direction detection.

### Pattern 3: PITCHING_IDEAL_RANGES Constant

**What:** Add alongside `IDEAL_RANGES` in `flags.ts`. Used by `MechanicsSidebar.tsx` for pitching angle display.

**Research findings (LOW-MEDIUM confidence — no authoritative prescriptive angle table found):**
- **Hip Drive (Hip Rotation) for pitching:** PMC11969493 reports 44 ± 12° pelvic rotation at ball release for collegiate pitchers. A reasonable ideal range for flagging is 35–60° (vs. hitting's 75–105°).
- **Arm Slot (Elbow Slot) during windmill:** The literature emphasizes near-extension during the top of the arm circle. During the back half and at release, elbow is more flexed. For a general elbow-slot flag in pitching, the "dropping elbow" threshold in hitting (< 70°) still applies, but the upper bound is wider — a pitcher's arm slot is more vertical. Range: 60–120°.
- **Shoulder Tilt in pitching:** Similar constraints as hitting — excessive tilt (> 20°) is undesirable. Keep same range as `IDEAL_RANGES.shoulderTilt`.


### Pattern 4: Gemini VLM Commentary Flow

**What:** Client button → POST to API route → Gemini 2.5 Flash → save to DB → return text → render.

**Full data flow:**
1. `AnalysisSummary.tsx` needs: (a) the contact frame's `isContact` marker, (b) access to the `HTMLVideoElement` ref (to capture the frame), (c) the `videoId` for DB persistence, (d) any existing `vlmSummary` text from initial load
2. `ReviewPageClient.tsx` must pass `vlmSummary` (loaded from `video_analyses.vlm_summary`) and the `videoId` down to `AnalysisSummary`
3. Frame extraction in browser: seek video to contact frame timestamp, wait for `seeked` event, then `canvas.drawImage(video)` + `canvas.toDataURL("image/jpeg", 0.8)` → strip `data:image/jpeg;base64,` prefix → send as `base64Frame`
4. API route POSTs to Gemini, saves result to `video_analyses.vlm_summary` via server-side Supabase client

**Contact Frame Extraction — Key Constraint:** `AnalysisSummary.tsx` is a pure presentational component with no ref access. The frame extraction requires a browser ref to the `HTMLVideoElement`. Two viable approaches:
- **Option A (preferred):** Extract the frame in `ReviewPageClient.tsx` (which already has `overlayRef`) and pass the `base64Frame` (or a callback) to `AnalysisSummary`
- **Option B:** Pass the `HTMLVideoElement` ref down as a prop to `AnalysisSummary` — violates separation of concerns
- **Option C:** Move the "Get AI Commentary" button out of `AnalysisSummary` into `MechanicsSidebar` where the ref is accessible via props — minimal code change

**Recommended approach (Option A):** Keep `AnalysisSummary` as a presentational component. Add an `onRequestCommentary: () => Promise<void>` callback prop. `ReviewPageClient` implements the callback (extracts frame, calls API), and passes the resulting `vlmCommentary: string | null` to `AnalysisSummary` as a prop.

### Anti-Patterns to Avoid

- **Detecting stride off power line using x-axis for side-view camera:** For side-view footage (required by the app's framing quality check), the stride direction is depth (z-axis in world coords), not lateral (x-axis in image). Use the normalized `z` coordinate from `NormalizedLandmark` or use hip-relative positioning. Flag this limitation in code comments.
- **Calling Gemini in a useEffect without abort controller:** Gemini calls can take 2-4 seconds. If the user navigates away, the call should be cancellable. Use `AbortController` or check component mount state before updating state after the async call.
- **Amending `SummaryFrame` without updating `AnalysisSummary` callers:** `SummaryFrame` is used in both `AnalysisSummary` and `MechanicsSidebar` (passed as `frames`). Adding `isContact` as optional (`isContact?: boolean`) is backward compatible.
- **Using `toDataURL()` before seeking completes:** Always await the `seeked` event after setting `video.currentTime` before drawing to canvas. See `usePoseAnalysis.ts` for the exact pattern already used in this codebase.
- **Showing "Get AI Commentary" button when analysis is not complete:** Gate the button on `analysisStatus === 'complete' || 'low_confidence'` and on a contact frame existing (`frames.find(f => f.isContact)` not null).

## Common Pitfalls

### Pitfall 1: Contact Frame Not in SummaryFrame Interface

**What goes wrong:** `AnalysisSummary.tsx` receives `SummaryFrame[]` which currently has no `isContact` field. The "Get AI Commentary" button cannot find the contact frame to extract.

**Why it happens:** `SummaryFrame` was defined as a lightweight shape for summary display — `isContact` was not included when the type was created.

**How to avoid:** Extend `SummaryFrame` with `isContact?: boolean`:
```typescript
export interface SummaryFrame {
  flags: MechanicsFlag[]
  angles: { hipRotationDeg: number | null; elbowSlotDeg: number | null; shoulderTiltDeg: number | null }
  isContact?: boolean  // NEW — true on the estimated ball-contact frame
  timestampMs?: number  // NEW — needed to seek video to correct position
}
```
Also pass `timestampMs` so `ReviewPageClient` knows where to seek the video for frame extraction.

### Pitfall 2: Stride Flag False-Positives on Side-View Camera

**What goes wrong:** The power line runs along the camera's depth axis (z) for side-view footage. A simple x-axis comparison flags every pitcher regardless of actual stride quality.

**Why it happens:** MediaPipe normalized x is image-horizontal. For a pitcher facing the camera side-on, x-axis measures how far the foot is toward the camera edge, NOT lateral stride direction.

**How to avoid:** Use the normalized `z` coordinate (MediaPipe estimates depth relative to the hip midpoint). A stride that crosses the power line would show a meaningful z-delta between the stride ankle and the drive ankle. Flag as `severity: 'warning'` with a code comment noting the camera dependency. Consider adding `[Experimental]` to the flag issue string or gating it with a lower confidence score.

**Warning signs:** If the stride flag fires on most pitching frames, the threshold or axis choice is wrong.

### Pitfall 3: Wind-Up Phase Isolation Without a Phase Classifier

**What goes wrong:** The Arm Circle (Bent Elbow) flag should only fire during the wind-up (when the arm should be extended), not during follow-through (when elbow naturally flexes). Without a phase classifier, it may fire on every frame.

**Why it happens:** `flagPitchingMechanics` is called per-frame with no phase context.

**How to avoid:** Use the contact frame index as the anchor. Frames BEFORE the contact frame are wind-up/stride/acceleration. Frames AFTER are follow-through.

Implementation: `flagPitchingMechanics` currently receives angles and landmarks but not frame context. Two options:
- **Option A (simpler):** Add an optional `isPreContact?: boolean` param to `flagPitchingMechanics` / `detectArmCircleBentElbow`
- **Option B (no signature change):** Call `detectArmCircleBentElbow` only for frames where `frameIndex < contactFrameIndex` — done in the caller (`flagMechanics` / `usePoseAnalysis`)

Option A is cleaner since `markContactFrame` runs AFTER all frames are collected, not during per-frame analysis. This means `flagMechanics` is called before we know which frame is the contact frame. **The practical solution:** Run the arm-circle flag on ALL frames but with a lenient threshold, since during follow-through the elbow is already past the ball-release point. OR add a note in the flag issue string distinguishing wind-up frames.

**Simplest pragmatic approach:** Set a threshold conservative enough that only clearly bent elbows (< 120°) get flagged. Pitchers often have near-extension (> 140°) during wind-up. A < 120° threshold will rarely fire during follow-through since the arm is moving fast past the release point.

### Pitfall 4: `AnalysisSummary` Is Not Connected to the Video Ref

**What goes wrong:** Extracting the contact frame as base64 requires `videoRef.current`, but `AnalysisSummary` has no ref access.

**Why it happens:** `AnalysisSummary` is a pure presentational component.

**How to avoid:** Extract the base64 frame in `ReviewPageClient` (which owns `overlayRef`) and pass it down via a callback or as a prop. Do not couple `AnalysisSummary` to DOM refs.

### Pitfall 5: Gemini Route URL Mismatch if Route is Moved

**What goes wrong:** If the route moves from `/api/analysis/vlm-eval` to `/api/analysis/vlm`, but the fetch call in the client still references the old path.

**How to avoid:** Decide the route path before building and use it consistently. Research suggests keeping `/api/analysis/vlm-eval` is lower risk (no rename). The CONTEXT.md marks this as Claude's discretion — keeping the existing path avoids the rename.

### Pitfall 6: vlm_summary Loaded on Page Init

**What goes wrong:** If `vlm_summary` is not fetched at page load, the existing commentary is invisible until the coach regenerates it, causing unnecessary API calls.

**How to avoid:** Two options:
- Add `vlm_summary` to the `video_analyses` SELECT in `usePoseAnalysis.ts` initialization query
- Fetch it in the server component (`page.tsx`) from `video_analyses` and pass down as a prop

The server component approach is cleanest (no client-side fetch needed). Add to `getVideo()` or add a separate `getAnalysis()` call in `page.tsx`.

```typescript
// To be implemented in ReviewPageClient.tsx
// Source: MDN HTMLCanvasElement.toDataURL() + existing seeked-event pattern in usePoseAnalysis.ts
const extractContactFrame = async (
  video: HTMLVideoElement,
  timestampMs: number
): Promise<string> => {
  video.currentTime = timestampMs / 1000
  await new Promise<void>((resolve) => {
    video.addEventListener('seeked', () => resolve(), { once: true })
  })
  const canvas = document.createElement('canvas')
  canvas.width = video.videoWidth
  canvas.height = video.videoHeight
  canvas.getContext('2d')!.drawImage(video, 0, 0)
  const dataUrl = canvas.toDataURL('image/jpeg', 0.8)
  return dataUrl.replace('data:image/jpeg;base64,', '')
}
```

## Open Questions

1. **Stride Off Power Line: x-axis vs z-axis**
   - What we know: MediaPipe `NormalizedLandmark.z` is a depth estimate (positive = in front of hip plane, negative = behind). For a side-view camera, stride direction IS depth-axis deviation.
   - What's unclear: Whether the MediaPipe z-coordinate has enough precision for this measurement. The documentation notes z is estimated and less reliable than x/y.
   - Recommendation: Implement with normalized x-axis offset first (simpler) with a low-confidence score and `[Experimental]` tag. If false-positive rate is high during manual testing, switch to z-axis or disable the flag for side-view footage.

2. **vlm_summary initial load: server component vs. client fetch**
   - What we know: `page.tsx` already fetches from `videos`; `usePoseAnalysis.ts` already fetches from `video_analyses`.
   - What's unclear: Whether to add `vlm_summary` to the page.tsx server query (cleanest, SSR) or the usePoseAnalysis hook query (avoids page.tsx changes).
   - Recommendation: Add to `usePoseAnalysis.ts` initialization SELECT — it's the same query path, no new server component changes needed.

3. **Arm Circle flag: fire on all frames or pre-contact only**
   - What we know: `flagMechanics()` is called during analysis (before contact frame is determined).
   - What's unclear: Filtering by frame phase without a phase classifier.
   - Recommendation: Use a conservative threshold (< 120°) so the flag fires only on clearly bent elbows. The follow-through phase will have different angular momentum patterns that make a sub-120° elbow transient and less likely to hit consistently. Document this design choice.
